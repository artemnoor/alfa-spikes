# T09 — векторизация результатов T08

Сервис получает четыре текстовых блока из результата T08 — тему, тип события, сущности и характер — и отправляет их одним пакетным запросом в Polza AI Embeddings API.

Используется модель `qwen/qwen3-embedding-8b`. PostgreSQL с pgvector возвращает топ‑10 новостей по взвешенному cosine similarity четырёх блоков. По умолчанию веса равные; `T09_BLOCK_WEIGHTS` принимает JSON, например `{"topic":1,"event":2,"entities":2,"genre":1}`. Health API показывает нормализованные веса. Один пакетный запрос JEV сравнивает новую новость с кандидатами, DeepSeek вызывается при сомнении и для проверки доказательств `RELATED`.

## Правила связи событий

- `SAME`: одно конкретное событие, сделка или договор. Публикации об этапах исполнения одного договора остаются `SAME`.
- `RELATED`: другое событие с доказанной связью с конкретным событием-кандидатом. Совпадения компании, продукта, отрасли или темы недостаточно. DeepSeek возвращает точные цитаты из обеих новостей; backend проверяет их наличие.
- `DIFFERENT`: независимые события, в том числе разные инциденты или контракты одной компании. Если текст прямо отделяет событие и указывает отличающуюся дату либо причину, срабатывает логическая проверка.
- `UNSURE`: фактов недостаточно; создаётся отдельная запись и задача ручной проверки.

Если JEV и DeepSeek расходятся между `SAME` и `RELATED` по одному кандидату, новость не объединяется автоматически и отправляется на ручную проверку.

Реестр SQLite объединяет новости `SAME` под одним `event_id`, хранит `RELATED` как связь между отдельными событиями и сохраняет историю решений. Контрольный бенчмарк не записывает свои статьи в реестр.

По умолчанию порог уверенности и минимальный разрыв кандидатов — `0.70` и `0.12`; это настраивается через `T09_MATCH_CONFIDENCE_THRESHOLD` и `T09_MATCH_MARGIN_THRESHOLD`. Порог экспериментальный, а уверенность JEV/DeepSeek не считается вероятностью фактической правильности.

При запуске PostgreSQL должен быть доступен по `T09_PGVECTOR_URL` из `backend/pipeline/.env`. Векторы хранятся как `vector(4096)`. Индекс приближённого поиска не создаётся: размерность Qwen 4096 выше ограничения HNSW для типа `vector`, а точный перебор соответствует небольшому текущему корпусу.

## Запуск

Из корня проекта запустите:

```powershell
$env:POLZA_AI_API_KEY = "ваш ключ"
npm --prefix backend/pipeline run seed
docker compose --env-file backend/pipeline/.env -f backend/pipeline/compose.yaml -p alfa-spikes-t09-pgvector up -d
npm --prefix backend/T09 start
```

Сервис слушает `http://127.0.0.1:8092`. Ключ можно задать в окружении процесса; код его не выводит. Параметры `PORT`, `POLZA_EMBEDDING_MODEL`, `POLZA_API_BASE_URL` и `CORS_ORIGIN` можно переопределить через переменные окружения.

## API

- `GET /health` — состояние Polza, PostgreSQL и число новостей, имеющих все четыре вектора.
- `GET /events` в сервисе архивной базы — реестр событий, сохранённые связи и очередь ручной проверки.
- `POST /vectorize` — принимает `newsId`, `title`, исходные `content`, `publicationDate`, `sourceKind` и `blocks`, массив из четырёх объектов `{ key, label, text }`, где `key`: `topic`, `event`, `entities` или `genre`.

Ответ включает embeddings, краткий preview, размерность, usage токенов, `topCandidates` с десятью новостями и их оценками JEV, а также `decision` с отношением, выбранным кандидатом, уверенностью, источником решения и итоговым действием. Если кандидат не найден, новая новость получает решение `DIFFERENT` без вызова LLM.

## Тесты и живой бенчмарк

```powershell
npm --prefix backend/T09 run test:all
```

`test:all` запускает 19 тестов классификационной логики с поддельным HTTP-провайдером, 4 теста SQLite-реестра, 2 интеграционных теста PostgreSQL/pgvector и 7 HTTP-тестов локального API. Для интеграционных проверок нужен работающий PostgreSQL из `backend/pipeline/.env`; модельные запросы в этих тестах не выполняются.

Живой бенчмарк выполняется отдельной командой и тарифицируется провайдерами:

```powershell
npm --prefix backend/T09 run benchmark:live
```

Он отправляет 111 контрольных новостей через работающий T09, Qwen Embeddings, JEV и DeepSeek по необходимости. Отчёт и сырые классификационные результаты сохраняются в `backend/T09/benchmark/runs/<run-id>/`. Отчёт включает сравнение весов на всём наборе кандидатов. Сценарии синтетические; эталонные метки назначаются воспроизводимыми правилами при генерации набора, а не независимыми экспертами. Вызовы к моделям реальные и тарифицируются. Каждая обработка остаётся в истории `stage_runs`; временные тестовые векторы удаляются после завершения прогона.

Последний полный прогон: [`RESULTS.md`](benchmark/runs/2026-10-16T18-26-23-708Z-9e0495a9/RESULTS.md) и [`results.json`](benchmark/runs/2026-10-16T18-26-23-708Z-9e0495a9/results.json). Проверены 111 историй: 98/111 совпадений отношения (88%), ожидаемый кандидат найден в top‑10 в 111/111, правильный кандидат выбран в 41/48 случаев SAME/RELATED. JEV выполнил 111 вызовов, DeepSeek — 47; известная стоимость JEV + DeepSeek — не менее 13,5492 ₽, цена Qwen embeddings не возвращается API. Все 10 профилей весов дали одинаковый ранг, поэтому данных менять равные веса нет. На 11 общих кейсах JEV-вход снизился с 6576 до 6540 токенов (-0,6%); набор слишком короткий, чтобы оценить эффект ограничения длинных статей. Это синтетическая проверка, а не независимый замер качества на новостном потоке. Отдельный живой регрессионный кейс после ограничения контекста: [`RESULTS.md`](benchmark/runs/2026-10-16T19-51-19-414Z-edde1038/RESULTS.md).

Если живой запуск остановился, он сохраняет `partial-results.json`. Продолжить оставшиеся кейсы без повторной оплаты уже завершённых можно командой `$env:T09_BENCHMARK_RESUME_FROM='путь\к\partial-results.json'; npm --prefix backend/T09 run benchmark:live`.
